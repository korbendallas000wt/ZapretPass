## Критический баг: неверный пароль уходит в блокчек

### Симптом

Пользователь вводит неверный пароль. Приложение сохраняет его и использует для запуска `blockcheck.sh` через `sudo -S`.

Последствия:

- блокчек стартует с заведомо неверными credentials;
- sudo может генерировать повторные неудачные попытки;
- процесс может зависнуть или вести себя непредсказуемо;
- сервис zapret может остаться в неправильном состоянии;
- пользователь получает ложные ошибки, не связанные с реальными стратегиями.

### Ожидаемое поведение

1. Пароль нельзя доверять только по факту ввода в диалог.
2. Перед любым привилегированным действием пароль должен проверяться, например через:

```bash
sudo -S -v
```

3. Если пароль неверный:
   - кэш пароля очищается;
   - keep-alive не запускается;
   - пользователь получает повторный запрос;
   - блокчек не запускается.
4. Если пароль валиден:
   - можно кэшировать;
   - можно запускать keep-alive;
   - можно передавать в `blockcheck.sh`.

### Где искать

Ориентировочно:

- `core/sudo.py`
- `ui/password_dialog.py`
- `ui/site_passport.py`
- `core/blockcheck.py`
- `core/service_manager.py`

Нужно проверить, где именно пароль сохраняется в кэш и откуда берётся перед блокчеком.

## Текущее состояние безопасности сценариев

### Auto-apply отключён

После инцидента с перезаписью `/opt/zapret/config` все:

```python
"apply_after": True
```

заменены на:

```python
"apply_after": False
```

Коммит:

```text
scenarios: отключено автоприменение стратегии после блокчека
```

Будущий блок `apply` должен быть только явным действием пользователя.

Добавлен `core/preflight.py`.

Он ищет:

- `nfqws`;
- `tpws`;
- `blockcheck.sh`.

Процессы делятся на:

- сервисные, если cgroup содержит `zapret.service`;

Если найдены сторонние процессы, блокчек не запускается.

Это важно, потому что `blockcheck.sh` требует полностью отключённых DPI bypass.

## Надёжная остановка блокчека — НЕ ЗАКРЫТА

Это вторая по важности задача после багa пароля.

### Проблема

Кнопка `⏹ Остановить блокчек` может не убивать всё дерево процессов.

Причины:

- отмена зависит от чтения `stdout`;
- `blockcheck.sh` может зависнуть без новых строк;
- дочерние `nfqws`/`tpws`/`curl`/`ncat` могут жить отдельно;
- `os.killpg()` может не хватать прав, потому что процесс запущен через `sudo`.

### Нужное решение

1. Watchdog-поток, который ждёт `cancel_event` независимо от `stdout`.
2. Убийство process group:
   - `SIGTERM`;
   - ожидание;
   - `SIGKILL`.
3. Если прямых прав нет — использовать sudo:

```bash
sudo kill -TERM -PGID
sudo kill -KILL -PGID
```

4. Реестр процессов, запущенных приложением:
   - PID;
   - PGID;
   - start_time;
   - kind;
   - cmdline.

5. При выходе приложения убивать только owned-процессы.
6. Не трогать `zapret.service` автоматически при выходе.

### Файлы для проверки/доработки

- `core/process_registry.py` — возможно уже создан, нужно проверить;
- `core/blockcheck.py` — нужен watchdog;
- `zapretpass.py` — нужен cleanup при старте/выходе;
- `ui/site_passport.py` — корректная обработка stopped/cancelled состояния.

## Прогресс-бар блокчека

Сейчас:

```python
setRange(0, 0)
```

Это неопределённый прогресс.

Точное количество тестов заранее неизвестно. Можно считать распознанные тесты по выводу, но нужно изучить `blockcheck.sh`.

Следующий шаг:

```bash
sudo grep -nE '^\s*\* |curl_test|port block|SUMMARY|press enter|strategies|test aborted|UNAVAILABLE|OK' /opt/zapret/blockcheck.sh | head -160
```

Затем сделать парсер:

- начало теста;
- конец теста;
- skip;
- abort;
- success/fail.

Для fast-режима лучше показывать не процент до конца, а:

```text
Проверено тестов: N
```

или

```text
Блокчек: найдено/проверено
```
