## Сессия 2026-09-17/18 — Создание ядра приложения

### Итог

Создано полноценное ядро приложения ZapretPass из 8 модулей, полностью отделённое от пользовательского интерфейса. Ядро не импортирует Qt и может тестироваться отдельно. Подготовлена документация для передачи контекста между сессиями.

### Хронология работы

1. Ревизия старого кода: 5 файлов на PyQt5 (zapret_gui.py, zapret_gui_tab1/2/3.py, sniffer_tab.py) и набор bash-скриптов.
2. Решение о переходе на Qt6 и переписывании проекта с нуля, а не адаптации старого кода.
3. Обсуждение архитектуры: симлинк-подход для движка, папка данных, структура модулей.
4. Создание структуры папок проекта: core/, ui/, data/, docs/, scripts/, installer/, assets/, tests/.
5. Перенос всех старых файлов в legacy/ (исключена из git).
6. Обновление .gitignore для защиты от мусорных файлов-доменов.
7. Создание модулей ядра (в порядке разработки):
   - core/config.py — пути и инициализация
   - core/service.py — управление systemd-сервисом
   - core/sudo.py — запрос и кэширование пароля
   - core/strategies.py — стратегии, whitelist, пресеты
   - core/blockcheck.py — запуск и парсинг blockcheck.sh
   - core/applier.py — применение стратегий к конфигу
   - core/sniffer.py — перехват SNI через tshark
   - core/checker.py — проверка доступности сайтов
8. Тестирование каждого модуля через python3 -c и pytest-подобные проверки.
9. Создание документации:
   - docs/STRUCTURE.md — карта проекта
   - docs/PROJECT_MANIFEST.md — карта модулей и форматов данных

### Модули ядра — краткая сводка

Все модули находятся в core/ и не зависят от UI.

- config.py — константы путей (PROJECT_DIR, ZAPRET_DIR), создание директорий, шаблоны конфигов whitelist/global, проверка установки движка.
- service.py — ServiceStatus dataclass, get_status() без sudo через systemctl show и cgroup, start/stop/restart/reload/enable/disable через sudo.
- sudo.py — SudoManager для запроса пароля через диалог (kdialog/Qt), кэширование в памяти, проверка через sudo -v, выполнение команд с привилегиями.
- strategies.py — сохранение результатов blockcheck, поиск пересечений/объединений стратегий для групп доменов, пресеты, whitelist.
- blockcheck.py — запуск blockcheck.sh с интерактивными ответами (8 параметров), парсинг секции SUMMARY, режимы full и fast.
- applier.py — применение whitelist, режима MODE_FILTER, стратегии к конфигу, бэкап и откат.
- sniffer.py — запуск tshark, извлечение SNI из TLS ClientHello, обрезка до базового домена, сохранение результатов.
- checker.py — проверка через curl (HTTPS, затем HTTP), классификация вердиктов (ok/partial/blocked/unknown).


### Ключевые архитектурные решения

**Почему Qt6 с нуля, а не адаптация старого кода**
Старый код содержал много дублирования и перемешанной логики (UI и бизнес-логика вперемешку). Адаптация PyQt5 кода в PyQt6 оказалась бы болезненнее, чем написание заново с чистым разделением на слои core/ и ui/.

**Почему ядро отделено от UI**
Все модули core/ не импортируют Qt. Это позволяет:
- Тестировать логику отдельно через Python-скрипты
- Менять интерфейс (например, с PyQt на PySide) без переписывания ядра
- Использовать ядро из командной строки или других инструментов

**Почему симлинк-подход для движка zapret**
Файлы движка лежат в папке проекта (PROJECT_DIR/engine/), но создаётся симлинк /opt/zapret -> PROJECT_DIR/engine/. Это даёт:
- Чистое удаление (убрать симлинк и папку)
- Совместимость со стандартными путями, на которые завязаны служба и конфиг
- Самодостаточность приложения (не зависит от пакетного менеджера)

**Почему systemctl show вместо systemctl status**
systemctl status выводит человекочитаемый текст, формат которого может меняться между версиями systemd и дистрибутивами. systemctl show выводит машинно-читаемый формат Key=Value, который стабилен. Это делает модуль мультисистемным.

**Почему PID читается из cgroup**
Сервис zapret запускается через sysv-обёртку и является Type=oneshot, поэтому MainPID часто равен 0. Реальный рабочий процесс nfqws живёт в cgroup, и его PID доступен через /sys/fs/cgroup/.../cgroup.procs.

**Почему MODE_FILTER читается из конфига, а не из вывода systemctl**
Вывод systemctl status может не содержать аргументы запуска в разных версиях. Чтение MODE_FILTER напрямую из /opt/zapret/config через регулярное выражение надёжнее и не зависит от формата вывода systemd.

### Решённые проблемы

**Проблема: определение режима сервиса (whitelist/global)**
Решение: чтение строки MODE_FILTER из конфига через регулярку r'^\s*MODE_FILTER\s*=\s*([A-Za-z_]+)'. Маппинг значений: hostlist/ipset/autohostlist -> whitelist, none -> global.

**Проблема: интерактивный ввод для blockcheck.sh**
Решение: отправка 8 ответов через stdin процесса (домен, ipver, http, tls12, tls13, quic, repeat, mode). Каждый ответ с переводом строки.

**Проблема: парсинг стратегий из вывода blockcheck**
Решение: поиск секции SUMMARY, извлечение строк с ":" и проверкой, что правая часть начинается с nfqws или tpws.

**Проблема: защита от мусорных файлов в корне проекта**
Решение: добавлены паттерны *.com, *.org, *.net, *.io в .gitignore для исключения случайного коммита файлов-доменов.

### Обсуждённые идеи (не реализованы)

**Fast-режим blockcheck**
Останавливаться на первой найденной рабочей стратегии, сразу применять её и запускать браузер, а полный перебор делать в фоне. Детектировать первый успех по маркерам в выводе (✓, OK, works, 200).

**Двухфазный поиск вспомогательных доменов**
Проблема: если основной домен заблокирован, браузер не пойдёт на вспомогательные домены.
Решение:
1. Блокчек на основной домен -> первая стратегия
2. Применить стратегию -> запустить браузер + сниффер
3. Блокчек на вспомогательные домены -> универсальная стратегия

**Предзагруженные списки вспомогательных доменов**
Для популярных сайтов (YouTube, Discord, X, Patreon) держать готовые sniffer_results/*.txt в комплекте. Это ускоряет работу для распространённых сайтов.

**Автозапуск браузера при сниффинге**
Открывать браузер поверх всех окон во время перехвата, чтобы пользователь мог взаимодействовать с сайтом и генерировать трафик к вспомогательным доменам.

**Управление несколькими стратегиями**
Сейчас конфиг хранит одну стратегию в NFQWS_OPT. Для разных доменов могут работать разные стратегии. Будущее: список стратегий с фильтрами по доменам.

## Сессия 2026-09-19/20 — Каркас UI на PyQt6

### Итог

Создан каркас главного окна ZapretPass на PyQt6:
- Вкладки сверху (3 шт: "Проверить и починить", "Мои сайты", "Дополнительно")
- Нижняя панель в GroupBox: строка статуса, круглый индикатор, кнопки Старт/Стоп/Рестарт
- Индикатор: красный (выключен), зелёный (все сайты), синий (whitelist)
- Сигналы для кнопок управления сервисом
- Точка входа: zapretpass.py

### Обсуждённые решения по интерфейсу

**Структура вкладок (путь чайника):**
- Вкладка 1: Диагностика → блокчек → карта сайта → тестирование стратегий
- Вкладка 2: Список сайтов с индикаторами, проверка доступности
- Вкладка 3: Продвинутые настройки (стратегии, сниффер, бэкапы)

**Алгоритм визарда для одного сайта:**
1. Диагностика (классификация блокировки)
2. Проверяем сохранённые стратегии (если есть)
3. Останавливаем сервис → полный блокчек (15-30 мин)
4. Применяем первую рабочую → сниффер → карта сайта
5. Тестируем все стратегии на карте сайта
6. Сохраняем лучшую → старт сервиса → проверка

**Хранение данных:** data/sites/{domain}.json с доменами, стратегиями, статусом

**Поведение при отмене блокчека:**
- Новый пользователь → дефолтный конфиг с пустым whitelist
- Сервис был включён → откат из бэкапа + старт
- Сервис был выключен → ничего не делать

### Технические решения

- PyQt6 (GPL подходит для открытого проекта)
- Системные цвета и стили (без хардкода), кроме индикатора (семантический светофор)
- Круглый индикатор вместо текстовой панели
- Нижняя панель в GroupBox для единого стиля
- Вкладки с рамкой (documentMode=False по умолчанию)

**Кэширование:** пароль запрашивается один раз при первой операции, затем кэшируется в `SudoManager` и продлевается фоновым таймером через `sudo -v`.

**CLI-режим:** отложен до востребованности (нужен только сисадминам).

## Сессия 2026-09-20 — Решение об архитектуре сценариев

### Проблема

Линейный визард с кучей условностей (if/else для разных ситуаций) превращается в нечитаемый спагетти-код. Каждый новый вариант использования добавляет новые ветки условий, и в итоге код невозможно поддерживать.

### Решение

Переход на архитектуру **сценариев** (Workflow Engine):

- Каждый сценарий — это последовательность блоков с флагами
- Блоки — это переиспользуемые этапы (диагностика, блокчек, сниффер, применение, сохранение)
- Флаги управляют поведением блоков в конкретном сценарии

### Структура
core/
scenarios.py ← Классы Scenario, ScenarioBlock, ScenarioRegistry
### Примеры сценариев

1. **🔧 Диагностика и починка** — сайт не работает, ищем стратегию
   - Диагностика → Блокчек → Сниффер → Применение → Сохранение

2. **🗺️ Расширение паспорта** — сайт работает, ищем вспомогательные домены
   - Диагностика → Сниффер → Сохранение

3. **🔬 Глубокий анализ** — все стратегии, все варианты
   - Диагностика → Блокчек → Сниффер → Тестирование → Сохранение

4. **⚡ Быстрая проверка** — только диагностика
   - Диагностика

### Флаги блоков

| Блок | Флаг | Описание |
|------|------|----------|
| diagnosis | stop_service | Останавливать ли сервис |
| blockcheck | mode | fast / standard / full |
| blockcheck | stop_service | Останавливать ли сервис |
| blockcheck | apply_after | Применять найденную стратегию |
| blockcheck | restart_service | Перезапускать ли сервис после |

## Сессия 2026-09-22/23 — Стабилизация сценариев, отмена блокчека и инцидент с конфигом

### Итог

Сессия началась с проверки сценариев после перехода на архитектуру Workflow Engine. Подтверждено, что базовая логика флагов работает: сценарий «Диагностика и починка» корректно запрашивает остановку сервиса перед блокчеком, а «Быстрая проверка» и «Расширение паспорта» не трогают сервис.

Закрыты или существенно улучшены несколько проблем из HANOFF:

1. Остановка сервиса перед `blockcheck`
   - После переустановки/очистки состояния zapret `service.get_status()` снова корректно видит активный сервис.

4. Пошаговое выполнение сценария

### Инцидент: автоматическая перезапись рабочего конфига zapret

Во время тестов было обнаружено, что YouTube перестал работать. Расследование показало, что дело не в саботаже и не в случайном внешнем изменении, а в собственной логике приложения.

Факты:

- `/opt/zapret/config` был изменён в `2026-09-22 20:46:24.533`.
- За 66 мс до этого был создан бэкап:
  - `/opt/zapret/config.backup.2026-09-22_20-46-24`
- Diff `config.before` -> `config.after` показал ровно одно содержательное изменение:
  - в конец конфига была добавлена новая строка `NFQWS_OPT=... --dpi-desync-ttl=2 ... --dpi-desync-fake-tls=0x00000000`.
- Запущенный процесс `nfqws` использовал именно эту добавленную строку, а не рабочую конфигурацию с `win_alt9`.

Причина:

- В сценарии «Диагностика и починка» у блока `blockcheck` стоял флаг:
  - `"apply_after": True`
- После завершения блокчека вызывался:
  - `service_manager.manager.cleanup_after_block(...)`
- Внутри `cleanup_after_block()` при `apply_after=True` вызывался:
  - `applier.apply_strategy(found_strategy, password)`
- `apply_strategy()` делал бэкап конфига и дописывал новую строку `NFQWS_OPT=` в конец `/opt/zapret/config` через:
  - `echo '...' >> /opt/zapret/config`
- В shell-конфиге побеждает последнее присваивание переменной, поэтому новая строка перекрывала предыдущую рабочую стратегию.

Действия по восстановлению:

- Текущий повреждённый конфиг был сохранён как forensic-копия.
- Восстановлен рабочий конфиг из:
  - `/opt/zapret/config.alt9.working`
- Сервис `zapret` перезапущен.

#### 2. Single-instance lock

В `zapretpass.py` добавлена защита от двойного запуска приложения через `QLockFile`.

Поведение:

- при первом запуске создаётся lock-файл;
- при повторном запуске показывается сообщение:

```text
ZapretPass уже запущен.
Закрой основное окно или заверши процесс.
```

- второе окно не стартует.

Это закрывает одну из ситуаций, когда пользователь случайно запускает несколько экземпляров и они начинают мешать друг другу.

#### 3. Preflight перед блокчеком

Создан модуль `core/preflight.py`.

Он проверяет наличие процессов обхода DPI перед запуском блокчека:

- `nfqws`;
- `tpws`;
- `blockcheck.sh`.

Важное различие:

- процессы внутри `zapret.service` считаются сервисными;

Если найдены сторонние DPI-bypass процессы, блокчек не запускается, а в UI показывается понятная ошибка.

Это уже реально спасло от невалидного блокчека: был пойман leftover `nfqws`, запущенный не из сервиса, а из пользовательской сессии/Konsole.

### Выявленные проблемы

#### 1. Критический баг: неверный пароль уходит в блокчек

Симптом:

- пользователь вводит неверный пароль в диалоге;
- приложение всё равно сохраняет/использует этот пароль;
- пароль передаётся в `blockcheck.sh` через `sudo -S`;
- блокчек стартует с заведомо неверными credentials;
- возможны повторные неудачные sudo-попытки, зависание, ложные ошибки, блокировка сервисных операций.

Ожидаемое поведение:

1. Пароль нельзя считать валидным только по факту ввода.
2. Перед запуском привилегированных операций нужно выполнять проверку через `sudo -v` или аналог.
3. Если пароль неверный:
   - кэш пароля очищается;
   - пользователь получает повторный запрос;
   - блокчек не запускается с невалидным паролем.
4. Keep-alive sudo-кэша не должен продлевать неверный пароль.

Это **P0 следующей сессии**.

---

#### 2. Остановка блокчека пока не гарантирует убийство всего дерева процессов

Была ситуация:

- пользователь нажимает `⏹ Остановить блокчек`;
- UI считает, что блокчек остановлен;
- но leftover `nfqws`/дочерний процесс может продолжать жить;
- при следующем запуске preflight справедливо блокирует блокчек.

Причина:

- текущая отмена частично зависит от чтения `stdout`;
- если `blockcheck.sh` завис на сетевой проверке или дочернем процессе, новых строк может не быть;
- `cancel_event` не проверяется, пока цикл чтения заблокирован;
- `os.killpg()` может требовать root-прав, потому что блокчек запускается через `sudo`.

Нужно:

1. Отдельный watchdog-поток, который не зависит от `stdout`.
2. Убийство всей process group через `SIGTERM`, затем `SIGKILL`.
3. При нехватке прав — `sudo kill -TERM -PGID` / `sudo kill -KILL -PGID`.
4. Реестр процессов, запущенных именно приложением.
5. Очистка owned-процессов при выходе приложения.
6. Нельзя автоматически трогать `zapret.service` при выходе — только процессы, запущенные приложением.

В конце сессии были подготовлены направления правок:

- `core/process_registry.py`;
- watchdog в `core/blockcheck.py`;
- cleanup при старте/выходе в `zapretpass.py`.

Но их нужно проверить/доделать в следующей сессии отдельным проходом, не смешивая с багом пароля.

---

#### 3. Сервис может остаться остановленным после прерванного сценария

В логах видно:

```text
service_was_active = True
Останавливаем сервис...
stop result: ok=True
```

А при следующем запуске:

```text
service_was_active = False
Пропускаем остановку
```

Это означает, что после предыдущего прогона сервис остался выключенным.

Возможные причины:

- приложение закрыли во время блокчека;
- блокчек остановили, но `cleanup_after_block()` не отработал;
- restart не выполнен из-за потерянного контекста `_service_was_active`;
- процесс блокчека остался жив и удерживал состояние.

Нужно продумать политику:

- при выходе приложения убивать свои процессы;
- при необходимости возвращать сервис в состояние, которое было до сценария;
- но не делать это молча, если пользователь явно остановил сервис.

---

#### 4. Прогресс-бар блокчека пока неопределённый

Сейчас используется:

```python
QProgressBar.setRange(0, 0)
```

Это честный режим «процесс идёт, но процент неизвестен».

Точное количество проверок заранее не известно, потому что его определяет сам `blockcheck.sh` в зависимости от:

- режима `quick/standard/force`;
- наличия `ncat`;
- DNS-проверок;
- port tests;
- HTTP/TLS1.2/TLS1.3/QUIC;
- повторений;
- досрочного abort;
- fast-режима.

Можно считать распознанные тесты по выводу, но сначала нужно закрепить стабильные маркеры в `blockcheck.sh`.
