## Сессия 2026-09-25 — Закрытие P0: Валидация пароля и Надёжная остановка блокчека

### Итог

Закрыты две критические инфраструктурные задачи из HANDOFF.md:
1. **P0 Пароль**: неверный пароль больше не уходит в `blockcheck.sh`. Внедрена принудительная проверка через `sudo -S -v` со сбросом кэша (`sudo -k`) перед каждым запросом. Добавлен механизм cooldown (временной блокировки ввода) после серии неудачных попыток.
2. **P0 Остановка блокчека**: реализован независимый watchdog-поток для управления жизненным циклом процесса `blockcheck.sh`. Устранены зависимости от чтения `stdout` при остановке. Добавлена защита от переиспользования PID через сверку `starttime`.

### Что сделано

#### 1. Безопасная валидация sudo-пароля (`core/sudo.py`)

- **Причина бага**: если у пользователя был активен системный кэш sudo, команда `sudo -S -v` возвращала успех, игнорируя ввод из stdin. Приложение сохраняло мусорный пароль.
- **Решение**: 
  - Перед проверкой пароля вызывается `sudo -k` для принудительного сброса кэша.
  - Проверка выполняется строго через `subprocess.Popen(['sudo', '-S', '-v'])`.
  - Результат интерпретируется только по `returncode == 0`. Тексты ошибок stderr логируются, но не парсятся (для совместимости с разными локали/дистрибутивами).
- **Cooldown/Lockout**:
  - После N неудачных попыток (по умолчанию 3) включается временная блокировка ввода пароля на M секунд (по умолчанию 30).
  - Во время блокировки диалог пароля не открывается.
  - После истечения таймера счетчик ошибок сбрасывается автоматически.
  - Параметры настраиваются через переменные окружения: `ZAPRETPASS_SUDO_MAX_ATTEMPTS`, `ZAPRETPASS_SUDO_LOCKOUT_SECONDS`.

#### 2. Надежная остановка процессов (`core/blockcheck.py`)

- **Watchdog-поток**: создан `_termination_watchdog`, который работает независимо от основного потока чтения вывода. Он следит за тремя событиями:
  - `cancel_event` (пользователь нажал "Стоп");
  - `timeout_event` (истек общий таймаут);
  - `fast_stop_event` (в режиме Fast найдена первая стратегия).
- **Безопасное завершение группы**:
  - Реализована функция `_terminate_process_group_gracefully`.
  - Цепочка сигналов: `SIGTERM` -> ожидание grace period -> `SIGKILL`.
  - Для Fast-mode используется цепочка `SIGINT` -> `SIGTERM` -> `SIGKILL`.
  - Используется polling `/proc/PID/stat` вместо `process.wait()`, чтобы избежать гонок между потоками.
- **Защита от переиспользования PID**:
  - Все проверки живости процесса привязаны к уникальному идентификатору запуска (`starttime` из `/proc/PID/stat`).
  - Если PID существует, но его `starttime` не совпадает с ожидаемым, процесс считается "не нашим" и не убивается. Это предотвращает случайное killing чужих процессов при быстром перезапуске приложений.
- **Реестр процессов**: интеграция с `core/process_registry.py` обеспечила корректную регистрацию и очистку owned-процессов. Сервисные процессы (`zapret.service`) автоматически не трогаются.

#### 3. UI-обработка ошибок пароля (`ui/site_passport.py`)

- Добавлен разбор причин отказа получения пароля (`last_failure_reason()`):
  - `locked`: показ виджета обратного отсчета до разблокировки.
  - `cancelled`: сообщение об отмене пользователем.
  - `invalid`: сообщение о неверном пароле.
  - `empty/no_dialog/expired`: специфичные технические сообщения.
- Внедрен виджет таймера ожидания повторного ввода (`_show_password_cooldown`).

### Коммиты этой сессии

- `e72ce56` fix(P0): валидация sudo-пароля, сброс кэша, повторные попытки.
- `d265cdc` docs(WORKLOG): закрыт P0 валидации sudo-пароля.
- `a895672` fix(blockcheck): надёжная остановка через watchdog, таймаут и fast-stop с защитой от переиспользования PID.
- `3ba5fc1` docs(WORKLOG): закрыта надёжная остановка блокчека.
- *(Локальные изменения в `core/sudo.py` и `ui/site_passport.py` по cooldown/UI пока не закоммичены)*.

### Выявленные проблемы и следующие шаги (P1/P2)

#### 1. UX Lockout и предупреждения (Требуется доработка)
Текущая реализация блокировки ("ранний перехват") неудобна:
- Пользователь теряет возможность запустить блокчек повторно сразу после окончания таймера из-за залипания состояния кнопки/воркера.
- Логика предупреждений несовершенна: лучше выводить явное предупреждение *"Осталась одна попытка перед блокировкой"* на предпоследней ошибке, а не просто молча блокировать.
- Нужно убедиться, что системные лимиты PAM/sudoers согласуются с app-level lockout, чтобы не провоцировать блокировку учетной записи ОС.

#### 2. Контракт диалогов пароля (`ui/password_dialog.py`)
Необходимо провести аудит всех реализаций ввода пароля (Qt, kdialog, zenity, lxqt, pkexec, terminal):
- **Единый контракт**: возврат `Optional[str]`.
  - `str` — непустой введенный пароль.
  - `None` — отмена, ошибка или недоступность диалога.
  - **Пустая строка `""` недопустима** как успешный результат. Особое внимание уделить `pkexec`, который может возвращать пустую строку с комментарием *"реальный пароль будет запрошен через sudo -S"*, что ломает новую схему валидации.

#### 3. Интеграционный тест остановки
Несмотря на успешные smoke-тесты на `sleep`, требуется живой тест реального `blockcheck.sh`:
- Запуск -> Остановка кнопкой -> Проверка отсутствия leftover-процессов (`ps aux | grep blockcheck`).
- Проверка очистки реестра owned-процессов.
- Проверка восстановления сервиса `zapret.service` (если он был активен до теста).

## Сессия 2026-09-25 — Адаптивный детект системных лимитов пароля

### Итог

Сессия была сфокусирована на P1 (UX lockout) и P3 (живой тест остановки блокчека) из HANDOFF.
Основной результат — приложение теперь не надстройка над системными лимитами, а адаптивный
клиент, который читает PAM faillock и sudoers passwd_tries и согласует своё поведение
с системными ограничениями.

### Что сделано

#### 1. Новый модуль `core/auth_limits.py`
Адаптивный детект системных лимитов аутентификации.
Читает конфиги **БЕЗ запроса пароля** там, где это возможно.

Алгоритм детекта:
- Проверяет наличие `pam_faillock.so` в PAM-файлах (`system-auth`, `common-auth`, `password-auth`)
- Читает параметры `deny`, `unlock_time` из `/etc/security/faillock.conf` (если есть)
- Если конфига нет — использует дефолты компиляции (`deny=3`, `unlock_time=600`)
- Пробует прочитать `passwd_tries` из sudoers через `sudo -n` (без интерактивного запроса)
- Если не удалось — использует дефолт `3`
- Итоговый лимит = минимум из всех системных лимитов

Публичный интерфейс:
- `max_attempts` — максимум попыток до блокировки
- `lockout_seconds` — длительность блокировки
- `warn_threshold` — номер попытки для предупреждения (предпоследняя)
- `is_account_locked()` — проверка блокировки учётки через `faillock --user`
- `get_lock_remaining_seconds()` — оставшееся время блокировки
- `get_system_lock_info()` — полная сводка для UI

#### 2. Single-instance lock

В `zapretpass.py` добавлена защита от двойного запуска приложения через `QLockFile`.

Поведение:

- при первом запуске создаётся lock-файл;
- при повторном запуске показывается сообщение:

```text

Закрой основное окно или заверши процесс.
```

- второе окно не стартует.

Это закрывает одну из ситуаций, когда пользователь случайно запускает несколько экземпляров и они начинают мешать друг другу.

#### 3. Preflight перед блокчеком

Создан модуль `core/preflight.py`.

Он проверяет наличие процессов обхода DPI перед запуском блокчека:

- `nfqws`;
- `tpws`;
- `blockcheck.sh`.

Важное различие:

- процессы внутри `zapret.service` считаются сервисными;
- процессы вне `zapret.service` считаются сторонними/leftover.

Если найдены сторонние DPI-bypass процессы, блокчек не запускается, а в UI показывается понятная ошибка.

Это уже реально спасло от невалидного блокчека: был пойман leftover `nfqws`, запущенный не из сервиса, а из пользовательской сессии/Konsole.

### Выявленные проблемы

#### 1. Критический баг: неверный пароль уходит в блокчек

Симптом:

- пользователь вводит неверный пароль в диалоге;
- приложение всё равно сохраняет/использует этот пароль;
- пароль передаётся в `blockcheck.sh` через `sudo -S`;
- блокчек стартует с заведомо неверными credentials;
- возможны повторные неудачные sudo-попытки, зависание, ложные ошибки, блокировка сервисных операций.

Ожидаемое поведение:

1. Пароль нельзя считать валидным только по факту ввода.
2. Перед запуском привилегированных операций нужно выполнять проверку через `sudo -v` или аналог.
3. Если пароль неверный:
   - кэш пароля очищается;
   - пользователь получает повторный запрос;
   - блокчек не запускается с невалидным паролем.
4. Keep-alive sudo-кэша не должен продлевать неверный пароль.

Это **P0 следующей сессии**.

---

#### 2. Остановка блокчека пока не гарантирует убийство всего дерева процессов

Была ситуация:

- пользователь нажимает `⏹ Остановить блокчек`;
- UI считает, что блокчек остановлен;
- но leftover `nfqws`/дочерний процесс может продолжать жить;
- при следующем запуске preflight справедливо блокирует блокчек.

Причина:

- текущая отмена частично зависит от чтения `stdout`;
- если `blockcheck.sh` завис на сетевой проверке или дочернем процессе, новых строк может не быть;
- `cancel_event` не проверяется, пока цикл чтения заблокирован;
- `os.killpg()` может требовать root-прав, потому что блокчек запускается через `sudo`.

Нужно:

1. Отдельный watchdog-поток, который не зависит от `stdout`.
2. Убийство всей process group через `SIGTERM`, затем `SIGKILL`.
3. При нехватке прав — `sudo kill -TERM -PGID` / `sudo kill -KILL -PGID`.
4. Реестр процессов, запущенных именно приложением.
5. Очистка owned-процессов при выходе приложения.
6. Нельзя автоматически трогать `zapret.service` при выходе — только процессы, запущенные приложением.

В конце сессии были подготовлены направления правок:

- `core/process_registry.py`;
- watchdog в `core/blockcheck.py`;
- cleanup при старте/выходе в `zapretpass.py`.

Но их нужно проверить/доделать в следующей сессии отдельным проходом, не смешивая с багом пароля.

---

#### 3. Сервис может остаться остановленным после прерванного сценария

В логах видно:

```text
service_was_active = True
Останавливаем сервис...
stop result: ok=True
```

А при следующем запуске:

```text
service_was_active = False
Пропускаем остановку
```

Это означает, что после предыдущего прогона сервис остался выключенным.

Возможные причины:

- приложение закрыли во время блокчека;
- блокчек остановили, но `cleanup_after_block()` не отработал;
- restart не выполнен из-за потерянного контекста `_service_was_active`;
- процесс блокчека остался жив и удерживал состояние.

Нужно продумать политику:

- при выходе приложения убивать свои процессы;
- при необходимости возвращать сервис в состояние, которое было до сценария;
- но не делать это молча, если пользователь явно остановил сервис.

---

#### 4. Прогресс-бар блокчека пока неопределённый

Сейчас используется:

```python
QProgressBar.setRange(0, 0)
```

Это честный режим «процесс идёт, но процент неизвестен».

Точное количество проверок заранее не известно, потому что его определяет сам `blockcheck.sh` в зависимости от:

- режима `quick/standard/force`;
- наличия `ncat`;
- DNS-проверок;
- port tests;
- HTTP/TLS1.2/TLS1.3/QUIC;
- повторений;
- досрочного abort;
- fast-режима.

Можно считать распознанные тесты по выводу, но сначала нужно закрепить стабильные маркеры в `blockcheck.sh`.
